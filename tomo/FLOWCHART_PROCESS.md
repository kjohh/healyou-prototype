# 原型拆解成流程圖 — 標準流程

從 `screen-flow.html` 的製作過程整理出的教訓，下次遇到類似任務時遵循此流程。

## 問題根源

直接開始實作，邊做邊發現錯誤：
- 誤用殘留的 CSS class（有定義但沒有對應 HTML）
- 看不出哪些元素是 JS 動態產生的
- 用猜的去還原畫面，而不是看實際結果

## 正確流程

### 第一步：程式碼審計（開始動手前）

閱讀原型程式碼，整理出以下清單後先給使用者確認：

1. **所有實際存在的畫面狀態**：HTML 中真實出現的 view/state，以及觸發條件
2. **殘留 CSS**：只有 CSS 定義、沒有對應 HTML 元素的 class（這次例子：`.ref-inline`、`.ref-panel`）
3. **JS 動態產生的元素**：不讀 JS 看不出來的 UI（這次例子：mood grid 的 `pal` 陣列、progress ring 的 stroke-dashoffset）
4. **狀態轉換邏輯**：動畫 timing、transition 參數、trigger 條件

輸出給使用者確認，等對方說「OK」再開始實作。

### 第二步：用瀏覽器工具自己截圖

使用 Chrome DevTools MCP 開啟原型，逐一觸發每個狀態並截圖，作為實作的視覺參考依據。不依賴猜測或使用者提供截圖。

```
流程：open_page → 操作觸發狀態 → take_screenshot → 對照實作
```

### 第三步：實作流程圖

以審計結果和截圖為依據，確保每個畫面都忠實反映原型實際樣貌。

---

## 使用者下次只需要說

> 「幫我把這個原型拆解成流程圖，先做審計再開始」

Claude 就會自動執行上面三個步驟，不需要使用者額外提供截圖或解釋程式碼細節。

## 這次踩到的具體錯誤（供參考）

| 問題 | 原因 | 應對方式 |
|------|------|----------|
| Reflection 用框框呈現 | 誤用 `.ref-inline`（殘留 CSS）| 審計時標記殘留 class |
| OB 背景色用暖色 | 沒讀 AMBIENT 陣列，用猜的 | 審計時列出動態色彩來源 |
| Mood grid 顏色/格數錯 | 沒讀 `pal` 陣列 JS 邏輯 | 審計時列出 JS 動態生成元素 |
| 進度環誤以為是 60s 倒數 | 沒讀 `setRingProgress()` 邏輯 | 審計時列出所有 UI 狀態函式 |
| 內容縮放 | 需求沒在開始時確認 | 審計問卷加入「尺寸規格確認」|
